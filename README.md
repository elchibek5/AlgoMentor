# AlgoMentor — Backend

Spring Boot API that analyzes an algorithm solution and returns a **strict, validated JSON
report**: correctness, complexity, edge cases, pitfalls, tests, and improvements.

The interesting problem here is not calling an LLM — it is refusing to pass along whatever the
model felt like returning. Every response is parsed, field-validated, and repaired-or-rejected
before it reaches a caller, so the API contract holds even when the model misbehaves.

> **Frontend:** [algomentor-frontend](https://github.com/elchibek5/algomentor-frontend) ·
> **Stack:** Java 21 · Spring Boot 3.5 · Maven

## Quick start

**No API key needed.** The project ships with a demo mode, so it runs on a fresh clone.

```bash
git clone https://github.com/elchibek5/algomentor-backend
cd algomentor-backend
./mvnw spring-boot:run
```

Verify:

```bash
curl http://localhost:8080/api/health
# {"ok":true,"mode":"demo","model":null,"message":"Demo mode: ..."}
```

**Requirements:** Java 21+. Maven ships with the repo via `./mvnw` — no separate install.

| | |
|---|---|
| API | <http://localhost:8080> |
| Interactive docs | <http://localhost:8080/api/swagger-ui.html> |
| OpenAPI spec | <http://localhost:8080/api/docs> |

## Demo mode vs live mode

| | Demo mode | Live mode |
|---|---|---|
| **API key** | Not needed | `OPENAI_API_KEY` required |
| **Analysis** | Generated offline from pattern matching | Generated by an LLM |
| **Cost** | Free | Billed per request by OpenAI |
| **Determinism** | Fully deterministic | `temperature=0`, but not guaranteed |
| **Use for** | UI work, tests, CI, trying the project | Actually reviewing code |

Demo mode returns a schema-valid response that reacts to what you paste — nested loops report
`O(n^2)`, hash-map solutions `O(n)`, sorts `O(n log n)` — but it is **not a real review**.
Every demo response says so in its `summary`, and the frontend shows a banner.

This matters for contributors: **you can develop and test almost everything without spending a
cent**, and CI runs the full suite with no secret configured.

### Switching to live mode

```bash
cp .env.local.example .env.local
# edit .env.local, set OPENAI_API_KEY=sk-your-actual-key
./mvnw spring-boot:run
```

`/api/health` should now report `"mode": "live"`. `.env.local` is gitignored.

If you leave the placeholder value in place, the server **stays in demo mode** instead of
failing against the real API with a confusing 401. See `DotenvBootstrap.PLACEHOLDERS`.

## How a request flows

```
POST /api/analyze
      │
      ▼
RequestLoggingFilter        assigns an 8-char request id, sets X-Request-Id,
      │                     puts it in the SLF4J MDC, logs method/path/status/ms
      ▼
AnalyzeController           @Valid triggers JSR-303 on AnalyzeRequest
      │                     → violations become 400 validation_failed
      ▼
AnalyzeService
      │  1. buildPrompt()       schema + rules + normalized mode + user input
      │  2. llm.analyzeToJson()
      │  3. tryParse()          slice from first '{' to last '}', deserialize
      │  4. if unparseable ──▶  one repair retry, then 502 invalid_model_output
      │  5. validateResponse()  every field checked; Big-O format enforced
      ▼
AnalyzeResponse             serialized as JSON
```

Anything thrown along the way lands in `ApiExceptionHandler`, which is the only place that
decides status codes and user-facing messages.

**Where to make changes**

| I want to… | Touch |
|---|---|
| Change what the model is asked | `AnalyzeService.buildPrompt()` |
| Change the output schema | `AnalyzeResponse` + `validateResponse()` + the schema in the prompt |
| Add or change validation on input | `AnalyzeRequest` annotations |
| Change an error's status or message | `ApiExceptionHandler` |
| Use a different LLM provider | Implement `LlmClient`, wire it in `LlmConfig` |
| Improve offline analysis | `DemoLlmClient.Shape.of()` |
| Change the coaching tone | `ChatService.buildPrompt()` |

## API reference

### `POST /api/analyze`

```bash
curl -X POST http://localhost:8080/api/analyze \
  -H "Content-Type: application/json" \
  -d '{
    "language": "java",
    "mode": "interview",
    "problem": "Two Sum",
    "constraints": "n up to 1e5",
    "solution": "class Solution { /* ... */ }"
  }'
```

| Field | Required | Constraint |
|---|---|---|
| `language` | yes | not blank, ≤ 30 chars |
| `solution` | yes | not blank, ≤ 20 000 chars |
| `mode` | no | `interview` (default) · `simple` · `deep`, case-insensitive |
| `problem` | no | ≤ 200 chars |
| `constraints` | no | ≤ 2 000 chars |

An unrecognized `mode` is rejected by validation; an absent one falls back to `INTERVIEW`.

<details>
<summary>Response shape</summary>

```json
{
  "summary": ["..."],
  "correctness": { "intuition": "...", "invariants": ["..."], "proofSketch": "..." },
  "complexity": { "time": "O(n)", "space": "O(n)", "explanation": "..." },
  "edgeCases": [{ "case": "...", "why": "..." }],
  "pitfalls": ["..."],
  "tests": [{ "input": "...", "expected": "...", "purpose": "..." }],
  "improvements": ["..."]
}
```

Guaranteed by `validateResponse()`: no list is empty, no string is blank, and
`complexity.time` / `complexity.space` match `^O\(.+\)$`. A response failing any of these is
never returned — the request fails with 502 instead.
</details>

### `POST /api/chat`

Free-form coaching, in contrast to `/api/analyze`'s strict schema.

```json
{ "question": "Why is my solution timing out?", "language": "java", "solution": "..." }
```
→ `{ "answer": "..." }`

`question` is required (≤ 20 000 chars); `language`, `problem`, `constraints`, `solution`, and
`context` are optional.

### `GET /api/health`

```json
{ "ok": true, "mode": "demo", "model": null, "message": "..." }
```

`mode` is `demo` or `live`; `model` is null in demo mode. The frontend calls this on load to
decide whether to warn that analyses are canned.

### `GET /api/debug/config`

Only registered under the `local`, `dev`, or `test` profiles. Reports whether a key was
resolved and the working directory — useful when dotenv loading is not behaving.

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

It reports **presence only**, never the key itself.

### Errors

Every failure returns `{ "error": ..., "status": ..., "message": ... }`.

| Status | `error` | Cause | Retryable |
|---|---|---|---|
| 400 | `validation_failed` | Bad request body; see the `fields` map | No — fix the request |
| 404 | `not_found` | Unknown route | No |
| 502 | `invalid_model_output` | Model returned unusable JSON twice | Yes |
| 503 | `llm_unavailable` | Provider down, key rejected, quota exceeded | Depends — read `message` |
| 500 | `internal_error` | Unexpected failure | Maybe |

Responses never carry stack traces or key material. Every response carries `X-Request-Id`,
which also appears in the logs — quote it in bug reports.

## Configuration

Resolution order for the API key: **environment variable → `.env.local` → `.env`**. A real
environment variable always wins, which is what you want in CI and containers.

| Variable | Default | Purpose |
|---|---|---|
| `OPENAI_API_KEY` | *(unset → demo mode)* | Enables live analysis |
| `SERVER_PORT` | `8080` | Port to bind |
| `APP_CORS_ALLOWED_ORIGINS` | `localhost:5173,localhost:5174` | Comma-separated frontend origins |

`src/main/resources/application.properties`:

| Property | Default | Purpose |
|---|---|---|
| `openai.model` | `gpt-4.1-mini` | Model id |
| `openai.baseUrl` | `https://api.openai.com/v1` | Point at any OpenAI-compatible endpoint |
| `logging.level.com.algomentor.backend` | `DEBUG` | App log verbosity |

Because `openai.baseUrl` is configurable, you can run against a local OpenAI-compatible server
(Ollama, LM Studio, vLLM) without touching code.

## Testing

```bash
./mvnw test                          # all 17
./mvnw test -Dtest=AnalyzeServiceTest       # one class
./mvnw test -Dtest=DemoLlmClientTest#reportsQuadraticTimeForNestedLoops
```

No API key required — `LlmClient` is mocked, and `DemoLlmClientTest` exercises the real
offline client. The suite is fully deterministic and makes no network calls.

| Test class | Covers |
|---|---|
| `AnalyzeServiceTest` | Parsing, the repair retry, rejecting missing fields and non-Big-O complexity |
| `AnalyzeControllerTest` | Request validation and status codes at the HTTP layer |
| `ChatServiceTest` | Response trimming, prompt content |
| `ChatControllerTest` | Chat endpoint validation |
| `DemoLlmClientTest` | Demo output passes the same validation a real response must |
| `AlgomentorBackendApplicationTests` | Context loads |

**Adding a test.** Service tests mock the seam and assert on behavior:

```java
LlmClient llm = mock(LlmClient.class);
when(llm.analyzeToJson(anyString())).thenReturn("""{ "summary": ["..."], ... }""");
AnalyzeService service = new AnalyzeService(llm, new ObjectMapper());
```

If you change `AnalyzeResponse` or `validateResponse()`, `DemoLlmClientTest` will fail until
`DemoLlmClient` produces the new shape. That is deliberate — it keeps the offline client from
drifting out of sync with the schema.

## Extending it

<details>
<summary><b>Use a different LLM provider</b></summary>

Implement the two-method seam:

```java
public class AnthropicClient implements LlmClient {
    public String analyzeToJson(String prompt) { /* return raw text */ }
    public String chat(String prompt) { /* return raw text */ }
}
```

Return the model's raw text — `AnalyzeService` handles extraction, parsing, and validation.
Throw `LlmUnavailableException` for provider failures so callers get a 503 with a useful
message. Then wire it in `LlmConfig.llmClient()`.

For an OpenAI-compatible API, set `openai.baseUrl` instead — no code needed.
</details>

<details>
<summary><b>Add a field to the analysis</b></summary>

Four places, in order:

1. `AnalyzeResponse` — add the field and its getter/setter
2. `AnalyzeService.buildPrompt()` — add it to the schema block in the prompt
3. `AnalyzeService.validateResponse()` — assert it is present and well-formed
4. `DemoLlmClient` — emit it, or demo mode starts failing validation

Then mirror the type in the frontend's `src/types.ts` and render it in `AnalyzePage`.
</details>

<details>
<summary><b>Add an analysis mode</b></summary>

Modes are normalized in `AnalyzeService.normalizeMode()` and described in the prompt's "Mode
behavior" block. Add the name to both, widen the `@Pattern` on `AnalyzeRequest.mode`, then add
it to the frontend's `Mode` type and `modeDescriptions`.
</details>

<details>
<summary><b>Improve offline analysis</b></summary>

`DemoLlmClient.Shape.of()` matches patterns in the submitted code and picks the complexity and
explanation. Add a branch — memoization, two pointers, binary search — and a case in
`DemoLlmClientTest`. Order matters: the first match wins, so put narrow patterns first.
</details>

## Design decisions

**A `LlmClient` interface, not direct API calls.** Prompting, parsing, and validation are the
parts worth testing, and they should not require a network or a key to exercise. The seam is
what makes the suite deterministic and free to run.

**One factory rather than competing `@Conditional` beans.** An earlier version annotated two
implementations and let Spring pick. `@ConditionalOnMissingBean` on a `@Component` depends on
scan ordering, which is fragile and unobservable. `LlmConfig` decides once, logs which mode it
chose, and exposes it to `/api/health`.

**Demo mode returns data instead of throwing.** Throwing made the project unusable for anyone
who cloned it — every analysis was an opaque 500. Returning a labelled, schema-valid response
makes the whole system explorable with zero setup, and doubles as a fixture for tests and CI.

**Validation duplicates what the prompt already asks for.** Prompts are requests, not
guarantees. `validateResponse()` is the actual contract; a `400` from a caller and a `502` from
a misbehaving model are different failures and should not look alike.

**Placeholder keys are treated as absent.** Copying an example file and forgetting to edit it
is the most common setup mistake. Falling back to demo mode explains itself; a 401 from OpenAI
does not.

**One repair retry, then give up.** Models usually recover when handed their own malformed
output. Retrying further mostly burns tokens and latency.

## Contributing

```bash
./mvnw test                    # before you push
./mvnw spring-boot:run         # manual check
```

- Conventional Spring Boot layout; constructor injection, no field injection
- Keep controllers thin — validation and routing only, logic in services
- Every new error path gets a case in `ApiExceptionHandler` with a message safe to show a user
- Never log or return key material
- Add a test for behavior you change; the suite must stay network-free

For larger changes, `AGENTS.md` documents the internals in more depth.

## Troubleshooting

**Port 8080 in use**
```bash
./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
```

**Health says `demo` but I set a key.** Confirm `.env.local` is in this folder (not the parent),
the value is not the placeholder, and you restarted. Then check
`/api/debug/config` under the `local` profile.

**`llm_unavailable`: "key was rejected."** Invalid or revoked. Generate a new one — OpenAI shows
a key only once at creation.

**`llm_unavailable`: "quota exceeded."** Billing, not code. Check usage limits in your OpenAI
dashboard.

**`invalid_model_output` repeatedly.** The model is ignoring the JSON-only instruction. Try a
more capable `openai.model`; check the logs for the raw text it returned.

**CORS errors from the frontend.** Add its exact origin to `APP_CORS_ALLOWED_ORIGINS` and
restart. Vite silently moves to `:5174` when `:5173` is taken, which is the usual cause.
