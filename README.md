# AlgoMentor — Backend

Spring Boot API that analyzes an algorithm solution and returns a **strict, validated JSON
report**: correctness, complexity, edge cases, pitfalls, tests, and improvements.

> **Frontend lives here:** [algomentor-frontend](https://github.com/elchibek5/algomentor-frontend)

---

## Run it in 60 seconds

**No API key needed.** The project ships with a demo mode so you can see it work immediately.

```bash
git clone https://github.com/elchibek5/algomentor-backend
cd algomentor-backend
./mvnw spring-boot:run
```

Open <http://localhost:8080/api/health> — you should see:

```json
{ "ok": true, "mode": "demo", "model": null, "message": "Demo mode: ..." }
```

That's it. Now start the [frontend](https://github.com/elchibek5/algomentor-frontend) and
paste some code.

**Requirements:** Java 21+. Maven comes bundled via `./mvnw` — you do not need to install it.

---

## Demo mode vs live mode

| | Demo mode | Live mode |
|---|---|---|
| **API key** | Not needed | `OPENAI_API_KEY` required |
| **Analysis** | Generated offline from pattern matching | Generated by an LLM |
| **Cost** | Free | Billed per request by OpenAI |
| **Good for** | Trying the project, UI work, running tests | Actually reviewing your code |

Demo mode returns a schema-valid response that reacts to what you paste — nested loops report
`O(n^2)`, hash-map solutions report `O(n)` — but it is **not a real review**. Every demo
response says so in its `summary`, and the frontend shows a banner.

### Switching to live mode

1. Get a key at <https://platform.openai.com/api-keys>
2. Create `.env.local` in this folder:
   ```bash
   cp .env.local.example .env.local
   ```
3. Replace the placeholder with your real key:
   ```
   OPENAI_API_KEY=sk-your-actual-key
   ```
4. Restart the server. `/api/health` should now report `"mode": "live"`.

`.env.local` is gitignored. If you leave the placeholder value in place, the server stays in
demo mode rather than failing with a confusing auth error.

## API

Interactive docs: <http://localhost:8080/api/swagger-ui.html>

### `POST /api/analyze`

```bash
curl -X POST http://localhost:8080/api/analyze \
  -H "Content-Type: application/json" \
  -d '{
    "language": "java",
    "mode": "interview",
    "problem": "Two Sum",
    "constraints": "n up to 1e5",
    "solution": "class Solution { /* ... */ }"
  }'
```

| Field | Required | Notes |
|---|---|---|
| `language` | yes | max 30 chars |
| `solution` | yes | max 20 000 chars |
| `mode` | no | `interview` (default), `simple`, or `deep` |
| `problem` | no | max 200 chars |
| `constraints` | no | max 2 000 chars |

Response:

```json
{
  "summary": ["..."],
  "correctness": { "intuition": "...", "invariants": ["..."], "proofSketch": "..." },
  "complexity": { "time": "O(n)", "space": "O(n)", "explanation": "..." },
  "edgeCases": [{ "case": "...", "why": "..." }],
  "pitfalls": ["..."],
  "tests": [{ "input": "...", "expected": "...", "purpose": "..." }],
  "improvements": ["..."]
}
```

### `POST /api/chat`

```json
{ "question": "Why is my solution timing out?", "language": "java", "solution": "..." }
```
→ `{ "answer": "..." }`

### `GET /api/health`

Reports liveness and which mode is active. The frontend polls this to decide whether to warn
the user that analyses are canned.

### Error responses

Every failure returns a JSON body with `error`, `status`, and a `message` you can show a user.

| Status | `error` | Meaning |
|---|---|---|
| 400 | `validation_failed` | Request body failed validation; see `fields` |
| 404 | `not_found` | Unknown route |
| 502 | `invalid_model_output` | Model returned unparseable JSON twice |
| 503 | `llm_unavailable` | Provider unreachable, key rejected, or quota exceeded |
| 500 | `internal_error` | Unexpected failure |

## Architecture

```
AnalyzeController ──▶ AnalyzeService ──▶ LlmClient (interface)
   REST + validation    prompt, retry,        │
                        parse, validate       ├── OpenAiClient   (live)
                                              └── DemoLlmClient  (offline)
```

`LlmConfig` picks the implementation once at startup based on whether a key is present, so the
active mode is deterministic and reportable rather than depending on bean-ordering.

**Reliability measures**

- JSON-only prompting; the response is parsed *and* field-validated before it is returned
- One automatic repair retry if the model emits invalid JSON
- Big-O format enforced on `complexity.time` / `complexity.space`
- `temperature = 0` for deterministic output
- No stack traces or key material in error responses

## Configuration

All settings have working defaults. Override via `.env.local` or environment variables.

| Variable | Default | Purpose |
|---|---|---|
| `OPENAI_API_KEY` | *(unset → demo mode)* | Enables live analysis |
| `SERVER_PORT` | `8080` | Port to bind |
| `APP_CORS_ALLOWED_ORIGINS` | `http://localhost:5173,http://localhost:5174` | Allowed frontend origins |

Model and base URL live in `src/main/resources/application.properties`
(`openai.model`, `openai.baseUrl`) — useful for pointing at an OpenAI-compatible endpoint.

## Troubleshooting

**Port 8080 already in use**
```bash
./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
```

**Health says `demo` but I set a key** — confirm `.env.local` is in this folder (not the repo
parent), the value is not the placeholder, and you restarted the server.

**`llm_unavailable` with "key was rejected"** — the key is invalid or revoked. Generate a new
one; note that keys are shown only once at creation.

**Frontend gets CORS errors** — add its origin to `APP_CORS_ALLOWED_ORIGINS` and restart.
